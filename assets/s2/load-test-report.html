06 · 작업 기준과 여유 관리

400RPS를 고정하고 CPU 사용량을 더 줄인다

500RPS에서 병목을 관측했으므로 후속 개선은 우선 400RPS를 기준으로 비교한다. 목록 API 외 다른 API도 같은 서버·DB를 사용하므로, 단일 API가 자원을 소진하지 않도록 여유를 남기려는 판단이다.

67.7%

400RPS APP CPU 평균

71.3%

400RPS DB CPU 평균

APPDB점선: 작업 참고선 70%

400RPS 본 측정의 1초 호스트 표본, 60개씩. 원본 host-app.json·host-db.json. 평균은 요청을 보내는 60초만 집계. 선은 관측 표본을 연결하며 순간 최대를 보장하지 않는다.

약 70%는 팀이 둔 여유 관리의 출발점이다. 보편적인 안전 상한은 아니다. DB 평균은 이미 71.3%로 참고선을 조금 넘었다. 남은 CPU 비율을 다른 API의 처리 용량으로 바로 환산할 수 없으며, 실제 API 비율을 반영한 혼합 부하 검증이 필요하다.

07 · 후속 개선 방향

같은 400RPS에서 개선안을 하나씩 비교한다

반복 DB 작업의 캐시 후보 검토

페이지마다 공유하는 COUNT 결과나 자주 조회하는 첫 페이지를 후보로 본다. 허용 가능한 지연 반영 시간, 무효화, 실제 적중률을 함께 검토한다. 이 자료에는 캐시 도입 이후 결과를 포함하지 않았다.

APP 메모리·GC·대기 비용 확인

CPU 평균만으로 여유를 판단하지 않고 메모리·GC·I/O 대기와 같은 시각의 응답 지연을 본다. 원인 증거 없이 커넥션 풀이나 스레드 수부터 늘리지 않는다.

400RPS 재측정 후 운영 비율 반영

응답시간·오류율·CPU·메모리·대기를 같은 방식으로 비교한다. 최종 운영 판단에는 다른 API의 사용 비율과 크레딧 장기 추세를 반영한다.

이번 단계의 결론은
“캐시 없이 400RPS를 60초간 무오류로 관측했다”

지속 가능 용량, PROD 성능, 모든 API의 동시 처리 용량은 별도 검증 대상이다.
